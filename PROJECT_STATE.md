# Content Calendar — Current State

## Purpose

`PROJECT_STATE.md` is the compact current-state memory layer for this tool. It answers "what is true now" so agents do not need to load the full `CHANGELOG.md` by default.

This file is a derived working summary. Exact implementation authority remains: source code, active config, and tests first; then this file; then README and `docs/decisions/`; then targeted changelog history.

## Current Architecture

Three cooperating CLIs share one SQLite database (`data/content.db`, gitignored):

- `generate_calendar.py` — generates a month of posts from a configurable posting cadence (`scheduling.py`), pushes them to Google Calendar, and persists one `content_slots` row per event. In the default `fifo` routing mode, every slot is untyped (`pillar_key = NULL`, no allocation). In `pillar` mode, weighted pillar allocation assigns a `pillar_key` per slot, as before.
- `process_content.py` — discovers `.mov`/`.mp4` files in `content/incoming/`, inspects/transcribes each, derives a caption candidate, and (in `pillar` mode only) classifies, then assigns the video to the earliest matching open `content_slots` row.
- `publish_tiktok.py` (Milestone 2.0) — manually publishes one already-assigned video to TikTok and persists the result in `platform_posts`. Not chained to the other two automatically — see "TikTok Publishing" below.

Google Calendar remains the human-facing source of truth for the schedule; `content_slots` is an internal mirror `process_content.py` queries and claims. See `docs/decisions/0001-video-ingestion-pipeline.md`, `docs/decisions/0002-configurable-cadence-and-weighted-pillar-allocation.md`, `docs/decisions/0003-local-embedding-classification.md`, `docs/decisions/0004-dedicated-google-calendar-ownership.md`, `docs/decisions/0005-fifo-baseline-and-optional-strategy-routing.md`, and `docs/decisions/0006-tiktok-publisher-foundation.md` for the full rationale.

The default `process_content.py` pipeline is fully local and requires no API key: ffmpeg + faster-whisper + SQLite, and (only in `pillar` mode) local embedding classification (`fastembed` + `BAAI/bge-small-en-v1.5`). Claude remains available as an optional classifier (`config.CLASSIFIER=claude`, pillar mode only) for comparison/benchmarking via `evaluate_classifier.py`.

## Routing Strategy (Milestone 1.3)

`config.ROUTING_MODE` (`CONTENT_CALENDAR_ROUTING_MODE`, default **`"fifo"`**) is an explicit, separately validated setting — never inferred from whether `CONTENT_TYPES` is populated. `scheduling.validate_routing_mode()` fails immediately and clearly on any other value.

- **`fifo`** — the default V1 automation path. No pillar or classifier is required or invoked: `generate_calendar.build_schedule()` produces untyped `OPEN` slots straight from the posting cadence and the future-only filter, and `process_content.py` never constructs a `ContentClassifier` in this mode at all (so an invalid/unset `CONTENT_CALENDAR_CLASSIFIER` cannot block it, and no embedding-model load cost is paid). Matching is `slot_matcher.select_slot_fifo`: earliest `OPEN` slot at/after now (inclusive), ingestion order, no pillar filter.
- **`pillar`** — the original Milestone 1/1.1/1.2 strategy, fully preserved and regression-tested: weighted allocation at generation time, classify → confidence gate → pillar-specific slot match at ingestion time. See "Active Pillar Strategy" below.

**Transcription is decoupled from scheduling in `fifo` mode only.** Media validity (ffprobe passes, audio stream exists) is still a hard precondition in both modes. But if `faster-whisper` itself fails on an already-valid video: in `fifo` mode the video is still scheduled (`videos.status="TRANSCRIPTION_FAILED"`, `transcription_status="FAILED"`, caption falls back to `caption_source="none"`) rather than being routed to `content/failed/`; in `pillar` mode this is unchanged from before — still a hard `FAILED`, since classification has nothing to work with otherwise. See ADR-0005 for why transcription is kept *before* (not after) slot assignment in the pipeline despite being non-blocking.

**FIFO ordering.** `process_content.discover_videos()` sorts a video already known to the database (still waiting in `content/incoming/` from a prior run) by its immutable `videos.created_at`, so its position survives the file being touched or copied — but not renamed, which is treated as a new video (documented limitation, not silently broken). A genuinely new file sorts by filesystem mtime, tie-broken by filename.

## Captions (Milestone 1.3)

`videos.caption_text`/`caption_source` (nullable) are first-class metadata, populated in **both** routing modes right after the transcribe stage, governed by `config.CAPTION_MODE` (`CONTENT_CALENDAR_CAPTION_MODE`, default `"transcript_auto"`):

- `transcript_auto` — `caption.build_caption_from_transcript()` normalizes whitespace only, **no truncation** (platform-specific length limits are deferred to the eventual per-platform publisher, not baked into the canonical stored caption). Falls back to `caption_source="none"` when the transcript is permanently unavailable (`TRANSCRIPTION_FAILED`).
- `manual` — never writes `caption_text` (no editing UI exists yet); only records `caption_source="manual"` so the stage is idempotent and never overwrites a future UI's caption.
- `none` — no caption generated.

No caption approval state machine (`DRAFT`/`APPROVED`/`AUTO`) yet — deliberately deferred, would not simplify anything without a UI. No `platform_posts` table yet either — video:post stays 1:1 until TikTok publishing actually exists; see ADR-0005 for the reasoning.

## Active Pillar Strategy (Provisional, `ROUTING_MODE=pillar` only)

As of 2026-09-12, `config.CONTENT_TYPES` is a **provisional** engineering-focused pillar set, replacing the earlier agency-oriented one, to test classification/routing against the content actually being produced now:

- `engineering` — **Software Engineering & Building** — 40%
- `career` — **Early-Career Software Engineering** — 30%
- `building_in_public` — **Building in Public** — 20%
- `mindset` — **Mindset & Discipline** — 10% (key unchanged from the prior strategy; label/description/weight updated)

This is a content-only change — no classifier, scheduling, persistence, or transcription architecture changed. The old pillar keys (`acquisition`, `building`, `execution`) no longer exist anywhere in `config.py`; `prompts.py` retired their prompt lists.

`prompts.py`'s `engineering`/`career`/`building_in_public` entries are **minimal placeholders** (3 short prompts each) added only to keep `PROMPT_GENERATION_ENABLED=True` functional — not a designed content plan. `mindset`'s prompt list is unchanged from the old agency-era strategy (same key, stale content) and does not yet reflect the new framing; designing real prompts for all four pillars is separate follow-up work. Prompts remain optional and never affect routing either way.

`EMBEDDING_MIN_SIMILARITY`/`EMBEDDING_MIN_MARGIN` were calibrated (loosely) against the old pillar set's semantics; they have **not** been re-validated against the new pillars with real transcripts. Treat them as still-uncalibrated placeholders until `evaluate_classifier.py --sweep` is run against a real labeled dataset built from the new content direction.

## Shofo Real-Video Evaluation Corpus (Milestone 1.3.1)

A test/evaluation utility, not a production feature — it does not change scheduling behavior. `download_shofo_samples.py` pulls a small (~12), reproducible (`--seed`), stratified sample of raw MP4s + reference metadata from the gated `Shofo/shofo-talking-head-en` Hugging Face dataset (~10k clips, ~104GB) into `evaluation/video_pipeline/` (gitignored except `README.md`) — never the full dataset, and never decoding video during row selection (`_disable_video_decoding()` disables Video-feature decoding before any row is pulled via `IterableDataset.decode(False)`, falling back to `Video(decode=False)` on older `datasets` versions — checking `ds.features` directly is unsafe, since that access peeks and decodes one row on a streaming dataset with an unresolved schema). `evaluate_transcription.py` then runs the real, production `transcription.FasterWhisperTranscriber` against each clip and reports WER/CER against the dataset's own WEBVTT reference transcript (a reference ASR output, not ground truth) plus `realtime_factor`. `transcript_metrics.py` holds the pure WEBVTT-normalization and Levenshtein-based WER/CER functions both scripts (and their tests) depend on.

**Verified real schema differs from the dataset card**: there is no `file_name` column — the downloadable reference lives inside the raw (non-decoded) `video` feature value as an `hf://datasets/<repo>@<revision>/<path>` URI, parsed by `_relative_path_from_video_field()`. `normalize_row()` is the one boundary function that translates Shofo's real field names to this project's internal manifest names (`_DIRECT_FIELD_MAP`); every other function (filtering, stratification, download, manifest) operates only on that normalized shape. Also confirmed by scanning the full metadata stream: `has_music` is `False` for all 10,000 rows in this dataset release (not a bug — the sampler's music alternation just has nothing to alternate with today). See `evaluation/video_pipeline/README.md` ("Observed Schema") for the full verified shape.

Neither script imports `content_store`, `slot_matcher`, `classification`, or `calendar_manager`. Dependencies (`datasets`, `huggingface_hub`) live in `requirements-eval.txt`, kept out of `requirements.txt` so the production dependency set is untouched.

This corpus is for media/transcription/FIFO testing only — **not** pillar-classification accuracy. The clips are arbitrary social talking-head content unrelated to `config.CONTENT_TYPES`; do not calibrate embedding thresholds or report pillar accuracy against it.

## TikTok Publishing (Milestone 2.0)

Proves `one known local MP4 → connected TikTok test account → TikTok API → private post → poll/check result → persist publishing result` for exactly one manually-chosen video — a standalone manual CLI (`publish_tiktok.py`), deliberately **not** wired into `process_content.py`, a scheduler, or any background process yet. See `docs/decisions/0006-tiktok-publisher-foundation.md` for the full architecture and rationale; this section is current-state only.

- **New table `platform_posts`** (`content_store.py`): one row per `(video_id, platform)`, `UNIQUE(video_id, platform)` enforced by the schema — the idempotency guarantee, not just caller discipline. Statuses: `PENDING`/`PUBLISHING`/`PUBLISHED`/`FAILED`. Preserves the three-way separation from ADR-0005: `videos` = canonical content/media metadata, `content_slots` = scheduling assignment, `platform_posts` = external publishing state/result — nothing TikTok-specific was added to `videos`.
- **`publisher.py`**: platform-neutral `Publisher` interface (`publish`, `get_status`) + `build_publisher()`, mirroring the existing `Transcriber`/`ContentClassifier` interface-plus-factory pattern. Only `"tiktok"` is registered; anything else raises `UnsupportedPlatformError` immediately.
- **`tiktok_publisher.py`**: `TikTokPublisher`, the only implementation. Queries the account's real `privacy_level_options` via `creator_info` before ever publishing (never assumes `SELF_ONLY` is offered), then Content Posting API v2's `FILE_UPLOAD` flow: `init` → `PUT` raw bytes to the returned `upload_url` → `status/fetch` to poll. All TikTok-specific request/response shapes live only here.
- **`tiktok_auth.py`**: TikTok OAuth, completely separate from Google Calendar's (different config vars, different cached token file at `~/.config/content-calendar/tiktok_token.json`, different scopes, no shared code). TikTok's OAuth has no loopback-server flow to rely on (unlike `calendar_manager.py`'s `InstalledAppFlow.run_local_server()`), so authorization is a deliberately manual two-command flow: `tiktok_auth.py --print-auth-url` then `--exchange-code <code>` (copied from the browser redirect). `get_access_token()` refreshes transparently afterward.
- **`publish_tiktok.py --video-id <id>`**: load video → verify local file exists and is TikTok-compatible (`media.is_tiktok_compatible`, reused) → verify a stored caption exists → `Publisher.publish()` → persist `platform_post_id` immediately (before polling, so a crash between submission and polling can't lose it) → `Publisher.get_status()` → persist outcome. `--poll-only` re-checks an in-flight submission without ever submitting.
- **Idempotency rule**: once `platform_post_id` is set for a `(video, platform)`, `publish()` is never called again under any circumstance — including a `FAILED` status, which is a distinct case ("TikTok accepted it, then reported failure") from a true submission failure (`platform_post_id` still `None` — safe to retry, reuses the same row rather than inserting a second).
- **Prerequisite fix in `process_content.py`**: `videos.canonical_media_path` was set once at inspect time (the `content/incoming/` discovery path) and never updated when the file moved to `content/processed/` on assignment — silently stale for any consumer reading stored state rather than re-discovering the file, which is exactly what `publish_tiktok.py` does. `_move_file` now returns the destination path, folded into the same `update_video` call that sets `status="ASSIGNED"`. The real database's 5 already-assigned Shofo videos were repaired to match.

**Real, live verification in this environment (up to the credentials boundary)**: `publish_tiktok.py --video-id 1` was run for real against the actual `data/content.db` and the real (post-repair) file at `content/processed/7000056250327174406.mp4` — it correctly resolved the video, passed the file-exists/TikTok-compatible/caption checks, attempted a real HTTP call, and failed with the clear, actionable "no TikTok credentials" error from `tiktok_auth.get_access_token()`, which was then correctly persisted as `platform_posts.status=FAILED` with `platform_post_id=NULL` (a true submission failure — safely retriable once real credentials exist, per the idempotency rule above; `scheduled_at` was correctly carried over from the video's assigned slot). **Not verified live in this environment**: everything past that point — the actual TikTok Developer Portal app setup, the manual OAuth authorization flow, and a real `creator_info`/`init`/upload/`status`/private-post round trip — since no TikTok developer credentials or dedicated test account were available here (same constraint as ADR-0004's Google Calendar OAuth). The exact request/response shapes in `tiktok_publisher.py` are implemented from TikTok's public API documentation, not confirmed against a live call. Automated tests mock every TikTok network call.

## Calendar Ownership

As of 2026-09-12, normal operation (`generate_calendar.py`/`clear_calendar.py` with no `--calendar` flag) targets exactly one dedicated, app-owned Google Calendar (`config.APP_CALENDAR_SUMMARY`, default `"Content Automation"`) — never `"primary"`, never an arbitrary calendar. Created/owned via OAuth (the human account), not the shared service account — see `docs/decisions/0004-dedicated-google-calendar-ownership.md`.

- `calendar_manager.resolve_app_calendar()` reuses the calendar ID persisted in `data/calendar_state.json` (gitignored); recovers by owner-only name search if that state is lost/inaccessible; creates a new calendar only if neither works. A calendar is created at most once per account.
- `clear_calendar.py`'s default path deletes only `content_slots` rows in `OPEN` status and their exact tracked calendar event — not a calendar-wide date-range wipe. `--all` extends this to `ASSIGNED` slots too, resetting the referencing video to `status=CLASSIFIED`/`assigned_slot_id=NULL` first (required by the FK on `videos.assigned_slot_id`) without touching its transcript/classification. The calendar itself is never deleted by either mode.
- `--calendar <id>` remains an explicit, opt-in override on both scripts, using the shared service account exactly as before this milestone (unchanged code) — never the default.
- **Not verified live in this environment**: creating this ADR's implementation required no Google Cloud OAuth Client ID to exist yet, and completing the interactive OAuth consent flow requires a real browser and the user's own Google Cloud Console access — neither available here. All calendar-ownership logic is verified via mocked-API tests (`tests/test_calendar_manager.py`, `tests/test_calendar_target.py`, `tests/test_clear_calendar.py`) plus real (unmocked) runs confirming dry-run touches nothing and the missing-OAuth-setup error is clear and fails closed. The one-time OAuth setup (README.md "Calendar Ownership" step) and the full live walkthrough (a real calendar actually appearing under the account, primary staying untouched) remain the user's manual step.

- `clear_calendar.py` — clears the dedicated calendar's `content_slots`-tracked events (`OPEN`, or `OPEN`+`ASSIGNED` with `--all`); `--calendar <id>` preserves the original service-account/date-range clear as an explicit override. Displays `[fifo]` rather than a pillar key for an untyped slot.

## Scheduling Strategy

- **Cadence/days/time:** `config.POSTS_PER_WEEK` (1-7), `config.POSTING_DAYS` (`"auto"`, evenly-spaced by `scheduling.auto_posting_weekdays`, or an explicit weekday list overriding auto), `config.POSTING_TIME` (`"HH:MM"`). A month's slot count is derived from actual calendar dates for the chosen weekdays, never `posts_per_week * 4`. This applies identically in both routing modes.
- **Future-only (as of 2026-09-12, unchanged by Milestone 1.3):** `scheduling.filter_future_dates` discards any candidate posting datetime before `start_at` **before** pillar allocation runs (pillar mode) or immediately becomes the slot set (fifo mode) — `generate_calendar.build_schedule(year, month, start_at=None, routing_mode=None)` resolves `start_at` via `slot_matcher.now_in_config_timezone()` when omitted, and `routing_mode` via `config.ROUTING_MODE` when omitted. The comparison is inclusive (`scheduled_at >= start_at`), so a same-day slot is kept if its `POSTING_TIME` hasn't passed yet. A month already partly elapsed is allocated (pillar mode) or sized (fifo mode) against only its remaining count, not the full month; an entirely past month returns `[]` and `generate_calendar.py` prints `No future posting slots remain for <Month> <Year>.` and returns before touching Google Calendar or `ContentStore` at all. A future month is unaffected (every candidate clears the boundary).
- **FIFO mode:** every future posting datetime becomes one untyped `OPEN` slot (`pillar_key=NULL`, `prompt=NULL`) — no allocation math runs at all.
- **Pillar mode allocation:** any number of `CONTENT_TYPES` entries, each with a `"weight"` (must sum to 1.0). `scheduling.allocate_pillars` uses the largest-remainder method for exact integer counts (computed against the future-filtered date count, not the full month); ties break by config (dict) order. `scheduling.distribute_pillars` then orders those counts across the month so pillars interleave instead of clustering. Prompts are attached only after date+pillar are decided, only if `config.PROMPT_GENERATION_ENABLED`, rotating per pillar through `PROMPTS[pillar_key]`. FIFO mode never attaches prompts regardless of `PROMPT_GENERATION_ENABLED`.
- **`content_slots` uniqueness is `scheduled_at` alone** (not `(scheduled_at, pillar_key)`) — one posting datetime is one slot regardless of which pillar a (possibly later-changed) strategy assigns it, or whether it has a pillar at all. `pillar_key` is nullable (Milestone 1.3, was `NOT NULL`). A database created under either the old two-column unique constraint or the old `NOT NULL` `pillar_key` is migrated automatically the first time it's opened (`content_store._migrate_content_slots_unique_constraint`, one rebuild pass covers both).

## Migration Safety: SQLite Cross-Table FK Rewrite On Rename

`_migrate_content_slots_unique_constraint` rebuilds `content_slots` via `RENAME TABLE content_slots -> content_slots_old` (SQLite has no in-place way to change a table's constraints). By default, modern SQLite's enhanced `ALTER TABLE RENAME` automatically rewrites any `REFERENCES` clause in *other* tables that pointed at the renamed table — so this rename silently rewrote `videos.assigned_slot_id`'s FK to say `content_slots_old`, and dropping that temporary table afterward left it dangling, pointing at a table that no longer existed. This surfaced as `sqlite3.OperationalError: no such table: main.content_slots_old` from `ContentStore.insert_video()` — confirmed against a real database's stored schema (`videos`' own `CREATE TABLE` SQL literally read `REFERENCES "content_slots_old"(id)`), not assumed from the traceback alone. SQLite raises this at DML statement-preparation time even for a row that never sets `assigned_slot_id` (it's left `NULL`) — the referenced table's existence is checked before the actual value is checked, not only when the constraint would be violated.

Fixed two ways, both empirically verified (not just asserted from documentation) against a real SQLite connection:

- **Prevention:** `_migrate_content_slots_unique_constraint`'s rename now runs under `PRAGMA legacy_alter_table = ON`, which suppresses that cross-table rewrite entirely — `videos`' FK text is left untouched by the rename. `PRAGMA foreign_keys` and `legacy_alter_table` must both be toggled *outside* any pending transaction (SQLite treats `foreign_keys` as a no-op mid-transaction), and the actual rebuild work (rename, recreate, copy, drop) runs inside one `BEGIN IMMEDIATE`/`COMMIT` so a failure never leaves a half-migrated table set — `Connection.executescript()` cannot be used inside that transaction (it implicitly commits any pending transaction first), so schema creation there uses plain `execute()` instead.
- **Repair:** `_videos_fk_needs_repair()` detects a `videos.assigned_slot_id` FK pointing at anything other than `content_slots` (via `PRAGMA foreign_key_list`, not string-matching the stale name) on databases that already migrated before the guard above existed. `_repair_videos_assigned_slot_fk()` fixes it the same safe way — rebuild `videos` under `legacy_alter_table = ON` (so the *reverse* corruption, `content_slots.assigned_video_id` getting rewritten to `videos_old`, can't happen either), copying every column by name (derived from `PRAGMA table_info`, not hardcoded) so it stays correct as `videos` gains columns over time. Verifies `PRAGMA foreign_key_check` is clean afterward as a hard safety check; raises rather than silently leaving a broken database if it isn't. Both `ContentStore.__init__` checks (`_videos_fk_needs_repair`, `_content_slots_needs_migration`) are cheap no-ops on an already-correct database.
- **Regenerating a month after changing the strategy is additive, not reconciling:** existing slots are never overwritten (`insert_slot_if_missing` skips any `scheduled_at` that already exists); only newly-covered timestamps get new slots. Mixing two strategies (or switching `ROUTING_MODE`) within one already-generated month is a known limitation, not a bug — see ADR-0002 and ADR-0005.

## Pipeline Behavior

- **Ordering:** a video already known to `content_store` (still waiting in `content/incoming/` from a prior run) sorts by its immutable `videos.created_at`; a genuinely new file sorts by filesystem mtime, tie-broken by filename (`process_content.discover_videos`, Milestone 1.3 — survives touch/copy, not rename; see ADR-0005).
- **Identity/idempotency:** videos are keyed by sha256 content hash. A video already `ASSIGNED` or `FAILED` is skipped on a re-run and reported as such; a video interrupted mid-pipeline resumes from its last completed stage (inspected fields, transcript, caption, and classification are all cached in `videos`).
- **Routing branch:** `fifo` mode skips classification entirely (no confidence gate, no pillar match) — every video with `status` in (`TRANSCRIBED`, `TRANSCRIPTION_FAILED`) that isn't yet `ASSIGNED`/`FAILED` is eligible for the earliest `OPEN` slot. `pillar` mode is unchanged: each classifier applies its own policy and returns `pillar=None` to abstain — `process_content.py`'s gate is simply `eligible = result.pillar is not None`. See Classification below for what each classifier's gate actually checks.
- **Transcription failure boundary (Milestone 1.3):** in `fifo` mode, a transcription failure sets `videos.status="TRANSCRIPTION_FAILED"` + `transcription_status="FAILED"` + `failure_reason` (from the taxonomy below) **without** moving the file to `content/failed/` or blocking slot assignment — the video proceeds to caption (falls back to `caption_source="none"`) and slot matching in the same run, and stays retriable for slot matching (never for transcription itself again) on subsequent runs. In `pillar` mode, transcription failure is unchanged: still routes to `status="FAILED"`, moved to `content/failed/`.
- **No slot available:** not a failure, in either mode. `assigned_slot_id` stays `NULL`; the next run retries slot matching automatically once more slots exist.
- **Failure taxonomy** (`videos.failure_reason`): `NO_AUDIO_STREAM`, `UNSUPPORTED_CODEC`, `CORRUPT_MEDIA`, `TRANSCRIPTION_FAILED`, `CLASSIFICATION_FAILED`, `MODEL_LOAD_FAILED`, `EMBEDDING_FAILED`, `INVALID_PILLAR_CONFIGURATION`. A hard-failed video (`status="FAILED"`) moves to `content/failed/`; an assigned one (including a FIFO video whose transcription failed but still got a slot) moves to `content/processed/`; anything `NEEDS_REVIEW`, or waiting for a slot (whether or not its `status` is `TRANSCRIPTION_FAILED`), stays in `content/incoming/`.
- **Backfill:** out of scope. Only `content_slots` rows written by `generate_calendar.py` after this feature shipped are eligible for routing — months generated before this landed must be regenerated.

## Classification (`ROUTING_MODE=pillar` only)

`fifo` mode never constructs or calls a classifier — the rest of this section applies only when `ROUTING_MODE=pillar`.

- **Default: `EmbeddingClassifier`** (`config.CLASSIFIER=embeddings`). Fully local via `fastembed` + `BAAI/bge-small-en-v1.5` (384-dim, ~65MB, cached at `config.EMBEDDING_CACHE_DIR`). Each pillar's `label + description + classification_examples` is combined into one profile text and embedded once per run; a transcript is embedded and compared to every pillar by cosine similarity. Auto-assigns only if the top pillar's similarity clears `config.EMBEDDING_MIN_SIMILARITY` **and** its margin over the second-best pillar clears `config.EMBEDDING_MIN_MARGIN` — otherwise `NEEDS_REVIEW`. **Both thresholds are explicitly uncalibrated placeholders** (`0.50`/`0.03`); use `evaluate_classifier.py --sweep` against real labeled transcripts to pick real values. `ClassificationResult.confidence` for this classifier is a raw cosine similarity, not a calibrated probability — never label it "% confidence" in output.
- **Optional: `ClaudeClassifier`** (`config.CLASSIFIER=claude`). Unchanged behavior from Milestone 1 except that it now applies `config.AUTO_ASSIGN_THRESHOLD` internally (previously this lived in `process_content.py`) and returns `pillar=None` below it. Requires `ANTHROPIC_API_KEY`; its absence still fails cleanly per-video (`CLASSIFICATION_FAILED`), not at startup.
- **Selection:** `classification.build_classifier()`, reading `config.CLASSIFIER`. An unknown value fails immediately: `Unsupported CLASSIFIER='foo'. Valid values: embeddings, claude`.
- **Evaluation:** `evaluate_classifier.py --classifier embeddings|claude [--sweep]` against `evaluation/` (private, real transcripts) or any `--dataset` path (e.g. the committed `tests/fixtures/eval_sample/`). Reports total/auto-assigned/review, auto-assigned accuracy, **wrong auto-assignments** (the metric to minimize), per-pillar accuracy, confusion pairs, and latency. Never touches `data/content.db`.
